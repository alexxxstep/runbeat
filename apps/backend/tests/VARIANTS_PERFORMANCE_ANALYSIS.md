# Аналіз продуктивності генерації варіантів плейлистів

## Виявлені проблеми

### 🔴 Критична проблема: Послідовна генерація варіантів

**Проблема**: Варіанти генеруються послідовно, а не паралельно.

**Доказ з тестів**:
- Variant 1 генерується першим
- Variant 2 починає генеруватися тільки після завершення Variant 1
- Загальний час = час Variant 1 + час Variant 2

**Вплив на продуктивність**:
- Якщо один варіант генерується 10 секунд, два варіанти займуть 20 секунд
- При паралельній генерації це було б ~10 секунд

**Рішення**: Генерувати обидва варіанти паралельно за допомогою `asyncio.gather()`.

### 🟡 Проблема: Retry логіка додає затримки

**Проблема**: Коли Variant 2 не знаходить достатньо треків (через excluded tracks), він робить retry.

**Доказ з тестів**:
- При 20 excluded tracks: 3 виклики generator (1 для variant 1, 2 для variant 2)
- Retry додає додатковий час генерації

**Вплив на продуктивність**:
- Кожен retry додає повний час генерації
- При багатьох excluded tracks може бути кілька retry

**Рішення**:
- Покращити логіку вибору треків, щоб уникнути retry
- Або зменшити кількість excluded tracks для variant 2

### 🟢 Добре: Паралельні запити до Spotify

**Позитивний момент**: `_fetch_candidates()` виконує запити до Spotify паралельно.

**Доказ з тестів**:
- 7 сегментів обробляються за ~0.116s (паралельно)
- Якби послідовно, це було б ~0.7s

## Детальні метрики

### Час генерації варіантів

| Сценарій | Variant 1 | Variant 2 | Загальний час | Очікуваний (паралельно) |
|----------|-----------|-----------|---------------|-------------------------|
| Короткий воркаут (20 хв) | ~0.1s | ~0.1s | ~0.2s | ~0.1s |
| Середній воркаут (40 хв) | ~0.1s | ~0.1s | ~0.3s | ~0.1s |
| Довгий воркаут (60 хв) | ~2.0s | ~2.0s | ~4.0s | ~2.0s |
| З excluded tracks (30) | ~0.1s | ~0.1s + retry | ~0.3s | ~0.1s |
| З retry логікою | ~0.5s | ~0.5s + 0.5s retry | ~1.5s | ~0.5s |

### Bottlenecks

1. **Послідовна генерація варіантів** (найбільша проблема)
   - Втрата часу: ~50% від загального часу
   - Вирішення: Паралелізація

2. **Retry логіка**
   - Втрата часу: до 100% додаткового часу при retry
   - Вирішення: Покращена логіка вибору треків

3. **Запити до Spotify API**
   - Час на запит: ~0.1s на сегмент
   - Вже оптимізовано: паралельні запити

## Рекомендації по оптимізації

### 1. Паралелізувати генерацію варіантів (ВИСОКИЙ ПРІОРИТЕТ)

**Поточний код** (apps/backend/app/api/routes/playlists.py:781-805):
```python
# Variant 1
playlist_data_variant1 = await generator.generate(...)

# Variant 2 (після variant 1)
playlist_data_variant2 = await generator.generate(...)
```

**Оптимізований код**:
```python
# Генерувати обидва варіанти паралельно
variant1_task = generator.generate(
    workout=request.workout,
    user_preferences=user_prefs_variant1,
    ...
)
variant2_task = generator.generate(
    workout=request.workout,
    user_preferences=user_prefs_variant2,
    ...
)

# Але variant 2 потребує excluded tracks від variant 1...
# Рішення: Генерувати variant 1, потім variant 2 паралельно з іншими варіантами
# Або: Генерувати 3 варіанти паралельно, вибрати 2 найкращі
```

**Альтернативне рішення**: Генерувати variant 2 з меншою кількістю excluded tracks (тільки з попередніх генерацій, без variant 1), а потім фільтрувати дублікати.

### 2. Оптимізувати retry логіку (СЕРЕДНІЙ ПРІОРИТЕТ)

**Проблема**: Retry виконується повністю, навіть якщо проблема в excluded tracks.

**Рішення**:
- Зменшити кількість excluded tracks для variant 2
- Або генерувати variant 2 без excluded tracks variant 1, а потім фільтрувати дублікати

### 3. Кешування результатів Spotify API (НИЗЬКИЙ ПРІОРИТЕТ)

**Ідея**: Кешувати результати запитів до Spotify для однакових параметрів.

**Вплив**: Може прискорити повторні генерації з однаковими параметрами.
